## Overview

Reify is a single-machine-first personal design agent. It turns a natural-language request into a plan, writes files step by step, streams code diffs and agent activity, runs structural, interaction, and syntax self-checks, and finally publishes the result as a reachable project. It is built for individuals, indie developers, and small teams who want to turn an idea into something presentable without understanding React, Next.js, or build tooling.

**Current branch**: `main`. **Production deployment**: host 55, `/data/reify-deploy` (containers `reify` / `reify-caddy` / `reify-sandbox`).

Design principles:

- **One sentence to a deliverable**: users describe what they want; the backend chooses the stack and delivery path automatically.
- **Visible process**: planning, file writes, self-checks, builds, and deployments are streamed as SSE events and can be viewed in Daily or Coding mode.
- **Templates plus general generation**: common requests use fast deterministic templates; long-tail requests are generated by an LLM, then validated for offline dependencies, structure, and syntax.
- **Local-first and secure by default**: accounts, sessions, projects, events, and artifacts live in local SQLite and the filesystem; generated content runs under a CSP sandbox or on a separate `:12889` origin.

## Features and templates

| Studio | Output | Automatic acceptance checks |
| --- | --- | --- |
| Mini-game | Snake / Tetris / airplane shooter / breakout, plus LLM-generated long-tail gameplay | Structure, viewport, scripts, canvas, offline self-check |
| Website | Built-in studio templates + LLM-generated landing pages | Structure, viewport, content sections, scripts, offline self-check |
| Resume | Built-in classic template + LLM-generated resumes | Structure, print styles, viewport, offline self-check |
| Travel guide | Built-in city itinerary template + LLM-generated guides | Structure, daily-route interactions, viewport, offline self-check |
| Image | Four locally stored images per request + gallery | Structure, image assets, viewport |
| Video | Asynchronous render + player page | Structure, video assets, viewport |
| Code | Built-in quicksort demo + LLM-generated algorithms | Structure, code presentation, `py_compile`, offline self-check |

The agent chooses the implementation automatically; the UI never exposes the stack. Mini-games, resumes, travel guides, images, videos, and code always use static templates. Company and studio sites default to static. Personal sites, portfolios, and blogs default to React when a sandbox is available. Next.js is only used when the prompt explicitly asks for Next.js/SSR: React generates a Vite project and builds a static `dist/`; Next generates an App Router project, builds a standalone artifact, and starts a Node server in a dedicated runtime sandbox. Source files remain visible in Coding mode.

Every static capability uses **built-in templates + general generation**:

- Games first try the built-in engines (Snake, Tetris, shooter, breakout); other genres (2048, Sudoku, endless runner, etc.) are generated as a single-file Canvas game from a GameSpec.
- Websites use built-in templates for studio/company/brand prompts; coffee shops, restaurants, events, and product launches go through general generation.
- Resumes default to the classic template; academic, medical, legal, and creative resumes use general generation.
- Travel guides default to the city itinerary template; road trips, camping, hiking, islands, and food tours use general generation.
- Code defaults to the quicksort demo; binary search, dynamic programming, graph algorithms, and similar topics use general generation (producing both `main.py` and a visualization page).
- Images and videos are model-driven; the built-in gallery/player only hosts the results.

Generated pages must pass structure, mobile, offline-dependency, and interaction/print/code checks, and may not reference external resources or make network requests. The first failure triggers one repair attempt; a second failure falls back to the built-in template so there is always a deliverable.

Platform features:

- Login/registration, multi-user project isolation, SQLite-backed server sessions, rate limiting, and auditing.
- Seven-template illustration gallery + a single general Composer that never exposes STACK/React/Next.
- Automatic static/React/Next routing; React and Next source projects are really built in OpenSandbox.
- Daily and Coding modes; file tree, line-by-line diffs, build logs, and event replay.
- Refine, redeploy, source export, public read-only links, and revoke.
- Next standalone runtime start/stop and blue-green switching; per-user runtime limits.
- Admin user table, enable/disable, session revocation, and audit log.
- Project library filters, statistics, recent projects, and 390px mobile support.
- Project deletion from both the card and detail page, with confirmation and cleanup of source, artifacts, events, runtime, and public links.

## Architecture

```text
                         HTTPS :12888
Browser ──────────────────────────────▶ Caddy
                                          │  TLS / ACME / SSE reverse proxy
                                          ▼
                              ┌─────────────────────────┐
                              │ FastAPI + React SPA     │
                              │ auth · SSE · projects   │
                              │ templates · admin       │
                              └───────┬─────────┬───────┘
                                      │         │
                     SQLite + workspace│         │ OpenSandbox API
                     data/reify.db     │         │ (builder / runtime)
                                      ▼         ▼
                              ┌─────────────────────────┐
                              │ Static artifacts / dist  │
                              │ Next runtime :12889     │
                              └─────────────────────────┘
                                      │
                              /p/ · /s/ · /apps/
```

A generation request flows as follows:

1. The frontend sends `{prompt, capability?}` to FastAPI; the backend classifies the capability and selects `static`, `react`, or `next` automatically.
2. The agent produces a plan, picks a built-in template or general generation, writes the workspace, and runs structure/interaction/syntax/offline checks.
3. Static results are published at `/p/{id}/`; React/Next source is sent to OpenSandbox for `npm ci` + build. Next can then start a standalone runtime.
4. Every step is written to the event stream and rendered live over SSE. Finished projects can be refined, shared, exported, or started as a runtime.

Trust boundaries: the platform UI/API lives on the trusted `:12888` origin; `/p/` and `/s/` run generated content under a CSP sandbox; Next SSR runs on the separate `:12889` origin, and `:12888` blocks `/apps/*`.

## Next.js SSR runtime

- When the prompt explicitly requests Next.js/SSR, the agent generates TypeScript sources such as `app/`, `app/api/notes/route.ts`, and `next.config.mjs`, runs `npm ci` + `next build` in OpenSandbox, and packages `.next/standalone`.
- After the build, "Start app" creates a dedicated runtime sandbox, uploads the standalone artifact, starts `node server.js` in the background, and marks the app `APP RUNNING` after a health check.
- The runtime defaults to 1 CPU / 1 GiB with a 1-hour TTL; the monitor stops it after 10 idle minutes. The current Docker runtime uses stop/start cold starts, not MicroVM pause/resume.
- On host 55, the OpenSandbox server joins both `reify-net` and the default `bridge`: the app calls it at `reify-sandbox:8080`, while the server proxies to sandbox `execd` over the bridge. Ports 41000-42000 are never exposed publicly.
- The sample app has a `/api/notes` server route that persists messages to the project volume (`runtime-data/notes.json`); the volume is a host bind provided by OpenSandbox and survives restarts.
- `/apps/{id}/` preview is disabled by default (`REIFY_SSR_PREVIEW=0`). Production uses a separate HTTPS port `:12889` in IP-only mode: platform on `:12888`, SSR apps on `:12889`. Caddy only exposes `/apps/*` on `:12889` and blocks `/apps/*` on `:12888`. The cloud security group must allow `12889`. Generated apps can still overwrite same-host cookies and cause logout (DoS), but cannot read platform cookies or API responses.
- Runtime endpoints: `GET /api/projects/{id}/runtime`, `POST .../runtime/start`, `POST .../runtime/stop`.
- "Continue editing" for React/Next patches the source and rebuilds; for Next it starts a new runtime, waits for the health check, then stops the old one (blue-green).

## React build and execution sandbox

- **Control plane**: a separately deployed OpenSandbox Server (`opensandbox/server`, Docker runtime) called through the Python SDK. The app container does **not** mount `docker.sock`.
- **One temporary sandbox per project/build**: `node:24-bookworm-slim`, 2 GiB by default (host 55 uses 4 GiB for Next builds), 1 GiB for runtimes; `cap-drop`, `no-new-privileges`, PID limits, and a 15-minute TTL; destroyed immediately after the build. Under the current Docker runtime, commands still run as the image's default user; non-root and read-only root filesystems require the MicroVM/secure runtime upgrade.
- **Source and logs**: source is written to `/workspace` through the file API; `npm install --ignore-scripts` and `npm run build` output is streamed back as `build_log` events.
- **Egress**: denied by default, allowing only `*.npmmirror.com`, `registry.npmjs.org`, and `*.npmjs.org`; no platform secrets are injected into the sandbox.
- **Artifacts**: after the build, `dist/` is packed, downloaded, size-checked, and atomically switched into `workspace/dist/`; a failed build keeps the previous artifact.
- **Publishing**: `/p/{id}/` serves only `dist/`; Vite JS/CSS assets use a project capability key so module loading works under the CSP sandbox without cookies.
- **Current limitation**: React/Next refinement is wired as "source patch → rebuild → switch", but requires an available LLM; SSR preview uses a separate port `:12889`, not domain-level isolation.

Enable the sandbox locally:

```bash
# 1. Start the OpenSandbox Server (Docker runtime)
uvx opensandbox-server init-config ~/.sandbox.toml --example docker
uvx opensandbox-server --config ~/.sandbox.toml

# 2. Start Reify
REIFY_SANDBOX=opensandbox \
REIFY_SANDBOX_DOMAIN=127.0.0.1:8080 \
REIFY_SANDBOX_API_KEY=your-sandbox-key \
REIFY_LLM_ENABLED=0 \
.venv/bin/python -m uvicorn server.main:app --host 127.0.0.1 --port 7801
```

See `.env.example` and the `[docker]` / `[egress]` sections of `deploy_remote.sh` for OpenSandbox configuration. The current setup uses Docker container isolation; it can later switch to ACS Agent Sandbox or OpenSandbox Firecracker for MicroVM isolation.

## Dual modes

- **Daily mode**: the agent timeline animates on the left; the result preview, acceptance checklist, and deployment status appear on the right.
- **Coding mode**: the timeline stays on the left; the right shows the file tree, line-by-line diffs, terminal logs, and live preview. Every agent step leaves a file snapshot that can be replayed.
- Both modes consume the same SSE stream and never rerun the agent.

## Accounts and access protection

- Anyone can self-register on the login page: usernames are 3-32 characters, passwords at least 8 characters, and registration logs the user in automatically.
- Accounts, scrypt password hashes, login sessions, project ownership, and runtime records live in local `data/reify.db` (SQLite WAL); sessions and projects survive restarts.
- Cookies contain only a random token; the session itself lives in SQLite. Logout, logout-all-devices, and password changes invalidate sessions.
- Login/registration is rate-limited by IP and username. Registration is open by default; set `REIFY_REGISTRATION=closed` to disable it.
- The first admin is created at startup from `REIFY_ADMIN_USER` / `REIFY_ADMIN_PASSWORD`; if no password is configured, a random one is printed to the startup log.
- The admin role is persisted and exposed at `/admin` with a user table, enable/disable, session revocation, and audit log. Regular users cannot read, modify, download, or preview other users' projects.

Existing single-password deployments keep the old `REIFY_PASSWORD` as the admin password; startup migrates flat projects to the first admin (the original directory is preserved). The deploy script backs up `data/reify.db` before upgrading. Manual migration:

```bash
.venv/bin/python scripts/migrate_v2.py --dry-run
.venv/bin/python scripts/migrate_v2.py
```

Login is rate-limited to 8 attempts/minute per user and 20 per IP by default; registration is limited to 5 per IP per hour. Caddy provides HTTPS: the app listens on internal `12888`, Caddy terminates TLS there using a public-IP certificate from Let's Encrypt (about 6 days, auto-renewed). Port 80 is used only for ACME HTTP-01 and redirects.

## Quick start

The console is a Vite + React + TypeScript SPA built into `web/dist/`; FastAPI serves it, so no Node process is required at runtime.

Prerequisites:

- Python 3.12+ (verified up to 3.14)
- Node.js 20+ (24 recommended) and npm, only for building the console and generated projects
- Static templates/general generation run without Docker; React/Next source generation also needs Docker + OpenSandbox

```bash
cd reify

# 1. Build the platform frontend
cd frontend && npm ci && npm run build && cd ..

# 2. Python environment
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

# 3. Optional: local environment variables (never commit)
cp .env.example .env

# 4. Start
REIFY_ADMIN_PASSWORD=your-admin-password \
REIFY_REGISTRATION=open \
.venv/bin/python -m uvicorn server.main:app --host 127.0.0.1 --port 7801
```

Open <http://127.0.0.1:7801>. The admin username defaults to `admin`; if no password is set, the startup log prints a temporary one. Other users can switch to "Register" on the login page.

Frontend hot reload (optional, in a second terminal):

```bash
cd frontend
npm run dev
# default http://127.0.0.1:5173
# if the backend is not on 7801: REIFY_BACKEND=http://127.0.0.1:12888 npm run dev
```

Enable the React/Next build sandbox locally:

```bash
# 1. Generate and start the OpenSandbox Server (Docker runtime)
uvx opensandbox-server init-config ~/.sandbox.toml --example docker
uvx opensandbox-server --config ~/.sandbox.toml

# 2. Start Reify with the same API key as the server
REIFY_SANDBOX=opensandbox \
REIFY_SANDBOX_DOMAIN=127.0.0.1:8080 \
REIFY_SANDBOX_API_KEY=your-sandbox-key \
REIFY_SSR_PREVIEW=1 \
REIFY_SSR_PORT=12889 \
.venv/bin/python -m uvicorn server.main:app --host 127.0.0.1 --port 7801
```

`run.sh` is equivalent to starting the backend on `0.0.0.0:12888`; it does not build the frontend, so run `cd frontend && npm ci && npm run build` first.

## Optional: any OpenAI-compatible model

Without a model, the agent uses a deterministic local director + template renderer, so every run produces a working artifact. With a model configured, it generates a short creative brief (title, tone, accent color, key points); long-tail pages and games also produce complete single-file deliverables. All other HTML is still rendered by verifiable templates to avoid broken model output. General generation disables thinking mode by default (`enable_thinking=false`) to avoid exhausting the output budget; if the model does not support it, set `REIFY_LLM_LONGTAIL_DISABLE_THINKING=0` and increase `REIFY_LLM_LONGTAIL_MAX_TOKENS`.

```bash
export REIFY_LLM_BASE_URL=http://127.0.0.1:8000/v1
export REIFY_LLM_API_KEY=sk-...
export REIFY_LLM_MODEL=qwen-plus
```

vLLM, SGLang, Ollama, and other OpenAI-compatible endpoints also work.

Images default to `qwen-image-3.0-pro` with four images per request; videos default to `wan3.0-video`, currently enabled in the workspace. `wan2.7-video` returns "Model not exist" in the current workspace; if enabled later, set:

```bash
REIFY_VIDEO_MODEL=wan2.7-video
```

Image/video assets are downloaded to `data/users/{uid}/projects/{id}/workspace/assets/v{revision}/`; the project page shows a gallery or player. Refinement creates a new `v{revision}` directory and keeps older assets. Asset URLs carry a project-level capability key so static pages can load them under the CSP sandbox.

### Inject model credentials safely

Write credentials to a local file, copy them to the server with scp, and never paste them into chat:

```bash
umask 077
cat > ~/.reify_llm.env <<'EOF'
REIFY_LLM_BASE_URL=https://your-provider/v1
REIFY_LLM_MODEL=your-model
REIFY_LLM_API_KEY=sk-your-key
REIFY_LLM_ENABLED=1
EOF

scp ~/.reify_llm.env root@117.148.166.55:/data/reify-deploy/.llm.env
ssh root@117.148.166.55 'chmod 600 /data/reify-deploy/.llm.env'
cd reify && ./deploy_remote.sh root@117.148.166.55 12888
```

The deploy script merges `.auth.env` and `.llm.env` into a 600-mode `.runtime.env` before injecting it into the container; it never writes secrets into the image, source, or Git.

To remove credentials after a one-off test, rebuild the container:

```bash
ssh root@117.148.166.55 'shred -u /data/reify-deploy/.llm.env /data/reify-deploy/.runtime.env'
rm -f ~/.reify_llm.env
cd reify && ./deploy_remote.sh root@117.148.166.55 12888
```

After the rebuild, `/api/health` reports `llm:false` and the template director keeps working.

## API

- `POST /api/auth/register` `{username, password, display_name?, email?}` → register and log in
- `POST /api/auth/login` `{username, password}` → log in (username or email)
- `POST /api/auth/logout` → revoke the current session
- `GET /api/auth/me` → current user
- `POST /api/projects` `{prompt, capability?}` → create a project; the backend selects static/React/Next, and the frontend never exposes the stack (`stack` remains available for internal tests)
- `POST /api/projects/{id}/refine` `{instruction}` → refine the current result conversationally (images/videos regenerate assets)
- `DELETE /api/projects/{id}` → delete your project and its files/runtime/public links; returns 409 while a task is running
- `GET /api/projects/{id}` → metadata + event history
- `GET /api/projects/{id}/events` → SSE event stream
- `POST /api/projects/{id}/deploy` → redeploy (static/React)
- `GET|POST /api/projects/{id}/runtime[/start|/stop]` → Next SSR runtime management
- `GET /apps/{id}/` → SSR preview (only when `REIFY_SSR_PREVIEW=1` and only for the owner)
- `GET /api/projects/{id}/bundle` → download the project zip
- `GET /p/{id}/` → deployed static artifact (owner only)
- `POST|DELETE /api/projects/{id}/share` → create/revoke a read-only share
- `GET /s/{token}/` → public read-only page (static/React; new projects are issued automatically)
- `GET /api/admin/users`, `POST /api/admin/users/{id}/status`, `POST /api/admin/users/{id}/revoke-sessions`, `GET /api/admin/audit` → admin APIs

After generation, static projects show a "Continue editing" input. The agent reads the current `index.html`, asks the model for a precise local patch, applies it, re-runs checks, and redeploys; a failed edit leaves the original page untouched. Every successful edit increments `revision` and appends to the same event stream. React/Next projects patch source files and rebuild; Next runtimes use blue-green switching (new runtime healthy before the old one stops).

## Account management and sharing

- Admins can view users, project counts, storage usage, and recent audits at `/admin`; they can disable/enable accounts and revoke all sessions for a user.
- New static/React projects automatically receive a read-only link `/s/{token}/`; `POST /api/projects/{id}/share` can reissue it and `DELETE` revokes it immediately. Share pages require no login but cannot call platform APIs; they expose only `index.html` and `assets/`, never source, README, or prompts. After revocation, old asset keys stop working for anonymous visitors, while the owner can still preview while logged in. Next SSR projects are not shareable yet.
- Each user can keep at most 2 running SSR apps (`REIFY_MAX_RUNTIME_PER_USER`); starting more returns 429.
- Passwords, sessions, and audits live in local SQLite; the audit log covers registration/login, project creation/refinement/deployment, runtime start/stop, sharing, and admin actions.
- Default per-user limits: 50 projects, 1 GB storage, 2 active tasks, 1 source build; exceeding a limit returns 429.

## Requirements

### Runtime

- Linux host + Docker Engine (24+ recommended) with `docker` / `docker network` permissions
- The platform container only needs Python 3.12; Node 24 is used only for image builds and project build sandboxes
- Production uses a Caddy container for TLS; no host Caddy/Nginx is required
- Browser E2E needs Google Chrome on the host (Playwright uses `channel=chrome`)
- Egress: npm builds need `registry.npmmirror.com` (configurable) and the LLM/media API domains; sandboxes use an allowlist by default
- Ingress: `80` (ACME HTTP-01 + redirect), `12888` (platform HTTPS), `12889` (SSR app HTTPS)

### Ports

| Port | Purpose | Exposure |
|---|---|---|
| 80/tcp | ACME HTTP-01, redirect | Public |
| 12888/tcp | Platform UI/API/SSE, `/p/`, `/s/` | Public |
| 12889/tcp | Next SSR `/apps/*` | Public (if Next runtime is enabled) |
| 8080/tcp | OpenSandbox Server | Docker network only |
| 3000/tcp | Individual Next runtime | Sandbox network only |
| 41000-42000 | Sandbox mapped ports | Bound to `172.17.0.1` only |

| Scenario | vCPU | RAM | Disk | Notes |
|---|---:|---:|---:|---|
| Static templates/general generation only, no source sandbox | 2 | 2 GB | 10 GB | App + Caddy + SQLite |
| Recommended full capability | 4-8 | 16 GB | 60 GB | React/Next builds + 1-2 SSR runtimes |
| Minimum for Next | 4 | 8 GB | 30 GB | Builds need a 4 GiB sandbox; higher concurrency queues |

Measured on host 55:

- Idle platform container about **55 MiB**, Caddy about **35 MiB**, OpenSandbox Server about **140 MiB**; the app container is limited to 2 vCPU / 4 GiB / 512 PIDs with `cap-drop ALL`
- React/Next build sandboxes: 1 vCPU / 4 GiB (overridden by the deploy script), concurrency 2
- Next runtime: 1 vCPU / 1 GiB, 1-hour TTL, stopped after 10 idle minutes
- Host 55: 96 vCPU / 251 GiB RAM / 30 GB disk, about 8 GB free after deployment; **disk is the bottleneck**, so clean dangling images or expand to 60 GB
- Platform image uses `python:3.12-slim` (~150 MB); sandbox Node image ~220 MB; default user storage quota 1 GB

## Remote deployment (HTTPS / Caddy)

### Prerequisites

- Linux host + Docker Engine; 4 vCPU / 16 GB RAM / 60 GB disk recommended
- Security group allows `80`, `12888`, `12889`; `80` is used for ACME HTTP-01
- The local machine can SSH to the target, and the target can pull Docker images and npm packages
- Optional: prepare `.llm.env` (never put keys in the repo or chat)

### First deployment

```bash
cd reify
./deploy_remote.sh root@117.148.166.55 12888
```

If the target still has an old `/opt/vibeforge` deployment, the script migrates automatically: copies data to `/data/reify-deploy`, copies `vibeforge.db` to `reify.db`, rewrites env prefixes to `REIFY_`, marks old runtimes stopped, and removes the old app/Caddy/sandbox containers after the new stack is healthy. The old directory is kept as a rollback backup. Because the cookie name changes from `vibeforge_session` to `reify_session`, all users must log in again. Migration only runs when `/data/reify-deploy/data` does not exist; set `REIFY_REMOVE_LEGACY=0` to keep old containers.

The script:

1. Syncs source to `/data/reify-deploy`
2. Builds `reify-app:latest` from `python:3.12-slim` (multi-stage Node build for `web/dist`)
3. Copies frontend output from the image to host `/data/reify-deploy/web/dist` (the container mounts `/data/reify-deploy` at `/app`)
4. Backs up `/data/reify-deploy/data/reify.db` to `/data/reify-deploy/backups/`
5. Generates/reuses `.auth.env` and `.sandbox.env`, and starts/reuses `reify-sandbox`
6. Replaces `reify` and `reify-caddy`, keeping the sandbox container
7. Verifies `/api/health`, 401 for unauthenticated `/api/projects`, and the React entry for `/login`

The first admin password is in:

```text
root@<host>:/data/reify-deploy/.auth.env
```

### Data, backups, and rollback

- All data lives in host `/data/reify-deploy/data/`; container rebuilds do not lose it
- Every deployment backs up SQLite to `/data/reify-deploy/backups/`; keep 7 days and copy off-host regularly
- Project artifacts are capped by `REIFY_MAX_STORAGE_PER_USER` (default 1 GB per user)
- Rollback: check out the previous Git revision and rerun the deploy script; database backups are in `backups/` (stop `reify`, replace `data/reify.db`, start `reify`)

### Updates and sandbox

- Rerun the deploy script to update; by default only app/Caddy are rebuilt, leaving existing SSR runtimes running
- After changing `.sandbox.env` or `sandbox/config.toml`, rebuild `reify-sandbox` manually; otherwise the old config stays active
- `REIFY_IMAGE` replaces the app base image; `REIFY_APP_IMAGE` only changes the tag and does not skip the build

### Certificates and verification

```bash
curl -kfsS https://117.148.166.55:12888/api/health
curl -kfsS -o /dev/null -w '%{http_code}\n' https://117.148.166.55:12888/login
```

Caddy uses a short-lived public-IP certificate with automatic renewal; the certificate and ACME account are stored in the Docker volume `reify-caddy-data`. If port 80 is unreachable, switch to a domain + DNS-01 or accept a self-signed certificate. `12889` is a separate origin; the platform on `12888` blocks `/apps/*` so generated apps cannot read platform cookies or API responses.

## Operations and troubleshooting

```bash
# Service and sandbox status
docker ps --format '{{.Names}}\t{{.Status}}' | grep reify
docker logs --tail 100 reify
docker logs --tail 100 reify-sandbox
curl -kfsS https://<host>:12888/api/health

# Data volume
docker exec reify python3 -c "import sqlite3; c=sqlite3.connect('/app/data/reify.db'); print(c.execute('select count(*) from users').fetchone(), c.execute('select count(*) from projects').fetchone())"

# Backup and restore (replace while stopped)
ls -lt /data/reify-deploy/backups | head
docker stop reify
cp /data/reify-deploy/backups/reify-<stamp>.db /data/reify-deploy/data/reify.db
docker start reify
```

Common issues:

| Symptom | Fix |
|---|---|
| 503 "React UI build is missing" | Run `cd frontend && npm ci && npm run build`; ensure `web/dist/index.html` exists |
| Login immediately bounces back | Production needs `REIFY_COOKIE_SECURE=1`; local HTTP needs `0` |
| React/Next tasks return 503 or config 503 | Check the sandbox container, API key, `reify-sandbox:8080` network alias, and `reachable` in `/api/health` |
| `npm ci` hangs | Ensure the build sandbox can reach `REIFY_NPM_REGISTRY`; do not point the lockfile at an internal registry |
| Next build OOM | Give the build sandbox at least 4 GiB and lower `REIFY_SANDBOX_CONCURRENCY` |
| 12889 unreachable | Allow 12889 in the security group; `12888` does not proxy `/apps/*` |
| Public page blank / React assets fail | Ensure `/s/` responses include `Access-Control-Allow-Origin: *` and `web/dist` is complete |
| General generation falls back to templates | Check the LLM config; keep `REIFY_LLM_LONGTAIL_DISABLE_THINKING=1` when supported, otherwise tune `MAX_TOKENS`/timeouts |
| Disk full | Clean dangling images (after confirming nothing uses them): `docker image prune`; long-term, expand to 60 GB |

## Security boundaries

- Self-registration + SQLite server sessions; unauthenticated pages redirect to login, APIs/previews return 401.
- Admins can disable users and revoke sessions; share links are read-only capability URLs that can be revoked; key actions are written to the local audit table.
- Public shares serve only `index.html` and `assets/`; README, source, and prompts are never exposed. After revocation, old asset keys stop working for anonymous visitors.
- Every project has a mandatory `owner_id`; all APIs, SSE, downloads, previews, and media check ownership or a project capability key. Cross-user access always returns 404.
- All `/p/` generated-content responses include `Content-Security-Policy: sandbox`, so opening them in a new window grants no same-origin access to the platform.
- Artifacts are written only to `data/users/{uid}/projects/{pid}/workspace/`; every file tool validates workspace paths.
- Static `/p/` preview iframes do not enable same-origin; Next preview on the separate `:12889` origin enables same-origin for its own `/apps/{id}/api/*` but cannot access platform pages on `12888`.
- The data layer is user-isolated; React/Next builds run in dedicated OpenSandbox sandboxes, and the app container has no `docker.sock`.
- Sandboxes receive no platform secrets and are destroyed after the build. npm registry allowlisting is the default; on host 55 the OpenSandbox egress sidecar cannot start, so the deploy script uses `REIFY_SANDBOX_EGRESS=open` (no sidecar) and isolation relies on container boundaries until the sidecar is fixed/replaced.
- The Next SSR runtime is a separate sandbox; `/apps/` preview is isolated by port `12889` vs. platform `12888`, and Caddy exposes `/apps/*` only on `12889`. Same-host cookie overwrite (DoS) remains possible.
- To open the platform to untrusted multi-user workloads executing arbitrary generated code, upgrade the Docker runtime to OpenSandbox Firecracker or ACS Agent Sandbox (MicroVM).
